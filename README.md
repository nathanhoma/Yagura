# Yagura

Yagura is a local recon and initial-access triage workspace. Import command results, review linked hosts/services/observations, inspect original evidence, and choose the next check from recorded findings. The backend runs on Python 3.10+ using only the standard library; the browser UI remains HTML and JavaScript.

## Run

```sh
python3 main.py
```

Open <http://127.0.0.1:8080>. On Kali, install `iproute2` and optionally `nmap` to use local discovery. Findings are stored in `data/findings.json`. The server binds to localhost by default.

If **Read local network state** reports that the API is unavailable or `Not found.`, check the address in the browser. This button sends `POST /api/discovery/local` to the same host and port that served the page. Start this project's Python server with `python3 main.py` and open its printed address. A static preview server or an older copy of Yagura may serve the page but lack that API route. For access from another machine, configure `APP_HOST` and `APP_PORT` on the machine running Yagura; the local network state shown is that server machine's state.

## Import and review

1. Select `nmap`, `ip addr`, `ip neigh`, `ping`, `httpx`, or `nuclei` in **Import command output**.
2. Paste the complete output or select a file up to 800 KB. Supply the source command and optionally the observation timestamp (entered in your browser's local time).
3. Preview the parsed records, then save the import. Inspect and correct records using **Edit**; saving marks them reviewed.
4. Use the target/service map and evidence links to inspect each relationship and original command output. **Merge** combines duplicates, preserves evidence, and redirects child links.
5. Export the complete graph and evidence as JSON, or finding rows with source commands as CSV.

| Parser | Supported output |
| --- | --- |
| nmap | Standard XML (`-oX`), or normal console / `.nmap` text; host states, port states, services, version details, script observations |
| ip addr | `ip -j addr` JSON or normal `ip addr` text, including IPv4/IPv6 interface addresses |
| ip neigh | `ip -j neigh` JSON or normal `ip neigh` text, including MAC/interface/neighbor state; `[]` represents an empty table |
| ping | Linux/iputils text and Windows text with a numeric target address; reply statistics and reachability observations |
| httpx | ProjectDiscovery JSONL with a numeric target IP; HTTP status, title, and technologies become linked observations |
| nuclei | ProjectDiscovery JSONL with a numeric target IP; template ID, name, and severity become linked observations requiring review |

XML preserves separate Nmap product and version fields. Normal text retains the full version description in `product`, because the text format does not consistently separate its components. Unrecognized or incomplete outputs return an error. A no-reply ping records `no-response`, which does not establish that a host is down. Re-imports deduplicate linked records while adding evidence; reviewed corrections survive later imports. Existing flat notes migrate automatically with a backup of the original file.

See [the common findings format](docs/findings-format.md) for fields, identity rules, timestamps, and merge behavior.

## Workflow and suggestions

The workspace has two operator-selectable modes. **AI automation** shows Investigation chat and Deep-dive candidates. **Manual control** shows Next checks and Email drafts; it can still use optional AI suggestions or a previewed short sequence, but the operator selects the checks. Scope and Findings are shared. The mode switch sits above the desktop sidebar navigation and moves into the main content when the sidebar is collapsed. Switching modes changes navigation and does not stop an active server-side investigation. Direct links to a mode-specific page select its mode automatically. In Manual control, the check list can be searched and initially shows five matches; optional assisted tools are collapsed until opened. The target map shows recon, service identification, and access triage stages. Confirm and save up to 16 authorized IPv4 CIDRs and optional domain suffixes in Scope. Each CIDR may contain up to 1,024 addresses, with up to 4,096 addresses total. RFC1918 and shared `100.64.0.0/10` ranges are supported, along with loopback and link-local ranges for local testing. The scope is saved in `data/scope.json`; an old single-`cidr` file is read automatically. Saving does not run discovery. Each scan or executable check requires separate confirmation.

**Deep-dive candidates** combines approved hosts, saved AI check outcomes, evidence-linked review flags, version-match leads, and recorded services. It sorts hosts by AI flags, version matches, rule leads, then missing results. Search and filters narrow the list. After a multi-host survey, Yagura automatically selects one approved host with imported evidence, records the evidence-based selection reason, and continues the one-host AI loop. Validated catalog commands run automatically; unlisted tools require human approval. Saved evidence analysis is available below the candidate list. The **AI deep dive** button preselects a host in the existing New investigation dialog; starting a run still requires the normal scope confirmation. A lead is not a confirmed vulnerability.

The **Inbox** button opens a right-side investigation inbox on every page. It puts human approval and discovery review first, summarizes each completed or stopped AI investigation once, and links back to the saved run. Running operations appear as brief progress cards. Individual completed checks are hidden by default and can be shown under Display. Run notifications come from persisted AI history, while live progress is in memory and resets on server restart. Read status and the check display preference are stored in this browser. Exact command approval remains in AI investigation with its confirmation dialog; the inbox never executes a check directly. Raw command output is not shown in the inbox.

Discovery accepts any subnet contained in the saved CIDRs, even when domains are set, but runs at a low global Nmap rate and saves newly seen IPs only in `data/discovery.json` as **unverified**. Discovery does not create executable findings. In Scope, enter one to four explicit internal resolver IPs that are also in the saved CIDRs, review PTR and A answers with resolver IP, time and TTL, then explicitly approve one forward-confirmed name/IP pair. Split resolver answers require a review reason. Only then is the host promoted into findings. In a domain-bound scope, older imported hosts also require this approval before executable suggestions or analysis; edits to an approved IP or name invalidate eligibility. Checks revalidate the current scope and approval on the server.

Large discovery ranges are split into `/28` segments (at most 16 addresses). Each `POST /api/discovery/scan` runs and saves one segment with a 90-second limit; the Scope page calls it sequentially and displays completed/total segments. A failed or timed-out segment stops the sequence without discarding earlier results. Selecting Discover again resumes at the first unfinished segment. Closing the page stops after the in-flight segment; `GET /api/discovery/pending` retains the progress and quarantined hosts. An already completed range is not rescanned automatically; select a narrower range to refresh selected IPs.

Built-in checks include ICMP reachability, common TCP ports, version probes, OS fingerprinting, web headers and inventory, SMB shares, and selected SSH/SMB/NFS scripts. TCP discovery and version checks use Nmap TCP connect mode (`-sT`). OS fingerprinting uses a fixed `sudo -n nmap -O` command against one approved host, limited to 100 common ports and one retry; noninteractive sudo is required. A scan without an OS match leaves the host OS unknown. Commands carry target and port values and link to evidence. They run without a shell, and parseable output is saved as linked findings. `httpx` and Nuclei JSONL can still be imported for review. Executable Nuclei and system-resolver PTR suggestions are disabled; DNS review instead uses only explicitly selected internal resolvers.

If `nxc` (NetExec) is installed, a recorded open 445/tcp service also offers **Inspect SMB host with NetExec** and **Check anonymous SMB shares with NetExec**. Both run against the approved numeric IP on port 445 only. The second check uses one empty username/password pair; Yagura does not accept credentials, modules, or extra NetExec flags in its command editor. A target SMB response is saved with the service and full command output as evidence. The Scope page reports whether `nxc` is available on the server.

The web inventory check pins each connection to the approved IP while preserving the configured hostname for virtual hosting. It reads up to five same-origin pages, the fixed `/robots.txt` and `/sitemap.xml` paths, and one randomized not-found baseline; it records 200/401/403/redirect responses, title, server header, bounded form metadata, up to 50 linked routes, up to 100 same-origin route hints from the metadata files, and baseline similarity. Listed paths are recorded without fetching them. Cross-origin redirects and forms are recorded but never followed or submitted. Query values and form values are not retained. The Findings view has a per-host Web survey of saved reports. No JavaScript is executed.

**Wappalyzer and Burp integrations:** In Findings → Import output, choose Wappalyzer JSON or Burp Suite XML and select the approved host. Yagura stores normalized metadata only; raw Burp requests, responses, cookies, and query values are discarded. In Findings → Web survey, **Run with Burp** can issue one `GET /` through PortSwigger's official Burp MCP extension and save its response status and content type automatically. Install and enable the extension in a running Burp Suite instance on the same machine, listening only on `127.0.0.1:9876`. The Python `requests` package is required for this optional integration. Yagura calls only `send_http1_request`, sets Burp's target to the approved literal IP, and asks for confirmation before the request. It does not expose Burp's history, scanner, Intruder, or configuration tools. HTTPS routing depends on Burp's handling of SNI for the IP-pinned connection; an HTTPS check may fail on virtual hosts. Burp issues remain observations to verify, not confirmed Yagura findings. Wappalyzer's official MCP/API requires a Business account and sends the target URL to Wappalyzer; Yagura does not call it, including for private exercise hosts.

**Local web technology detection:** The executable **Identify web technologies** check uses Yagura's built-in IP-pinned HTTP(S) transport. It makes one root-page GET on an approved recorded web service, retains certificate verification, and does not follow redirects or links. Curated signatures inspect server and framework headers, generator metadata, and a few page asset markers for technologies such as nginx, Apache, PHP, WordPress, Drupal, Next.js, and Angular. Findings → Web survey shows each technology, any reported version, signal source, and confidence. Saved evidence contains only this normalized report; raw page HTML, cookies, and unrelated headers are discarded. This is a limited detector, so an absent signal does not mean the technology is absent, and a reported version must be verified before assessing vulnerabilities. The check can run from Next checks or AI investigation without a Wappalyzer account, external API, browser extension, or additional runtime dependency.

In **Next checks**, **Edit & run** opens the suggested command for review. The server accepts bounded changes to ping count (1–5), Nmap top-port count (1–1,000), recorded service ports or version level, and HTTP header timeout (1–20 seconds) or same-origin path. Other commands can be rerun unchanged. The program, target, and required options cannot be changed in this editor. The edited command is checked against the current candidate and saved scope, executed without a shell, and recorded as the evidence source command. The same authorization checkbox is required for Run and Edit & run.

**Short automatic check run** in Next checks lets you select one approved host and preview up to three exact commands before starting. It uses a limited set of reachability, TCP port/service, HTTP header, and SSH host-key checks. The browser runs the listed commands in order through the existing checked execution API; it never adds newly suggested commands mid-run. Before each command, it compares the saved scope and current candidate with the preview. It stops on no ICMP reply, a failed check, an import warning or missing import, a changed scope or candidate, or a stop request. Stop takes effect after any check already in progress. Each result and the stopping reason remain visible in the page until another preview is made. Closing the page ends the sequence after any in-flight check; there is no background job.

**Request a check in plain language** in Next checks accepts one operator request for one approved host. When an existing read-only candidate fits, the AI can adjust bounded parameters; the server validates the same program, target, pin and mandatory options before saving. AI-generated Nmap top-port checks are limited to 100; HTTP header checks are limited to a same-origin path without query values and a 10-second timeout. These bounded proposals can run only after the normal authorization checkbox and another scope/command check.

If no bounded candidate fits, the AI may also write a single-line **manual proposal**. It is saved in `data/check-proposals.json` with a pending-review state. A person must inspect the complete command and explicitly approve or reject it; only an approved, current-scope proposal receives a Copy button. Yagura **never executes manual proposals**, even after approval, because arbitrary programs may create uncontrolled network connections or side effects. The reviewer must independently verify every destination, option, credential and consequence before using such a command in an authorized environment. Creating or reviewing a proposal never runs it. This review action does not assert that the command is safe; it records only that a person examined it.

After an approved manual command has actually been run, the operator can record its output against that exact proposal. This imports sensitive evidence and adds a host-specific, **reference-only** entry to the built-in check templates and saved references. Approval alone does not add it, and catalog registration never makes the command eligible for Yagura execution or AI-led runs. Review destinations and authorization again before any later reuse.

**Investigation chat** shows the active run, saved plans, check results, observations, review flags, and stop reason as conversation turns. A run picker opens any saved investigation. New investigation opens the host-survey or scope-discovery controls in a dialog; the command approval card stays immediately above the composer while review is required. Approve, revise, and reject act on the exact current proposal, and approval still requires a confirmation dialog. The technical AI investigation log remains available by direct link for diagnostics. Start controls cover one-host, multi-host survey, and scope-discovery modes. The multi-host picker supports search and shows selected hosts. Saved runs show their outcome before the expandable event log. It starts a separate server-side, AI-led run on one explicitly approved host after operator confirmation. After each imported tool check, the model receives newly saved, redacted evidence and chooses the next tool or stops. From the first AI investigation step, the model selects a tool by name and constructs an exact command from saved evidence. For catalogued installed tools, Yagura reads only the selected tool’s local help. An installed tool absent from the catalog can also be proposed, but Yagura does not run its help and marks it for explicit human review. The proposed executable must match the selected tool. Catalogued tool commands run automatically only after tool-specific validation of the approved target, bounded options, and destinations. Unlisted tools wait for exact human approval. For unlisted tools, the run pauses until a human approves the exact text, requests a revision in plain language, or stops it. Every revision needs fresh approval; the approval is bound to the exact canonical command and revision. Before every execution, Yagura rechecks the saved scope and host and executes the command as the server user without an implicit shell, imports the result, and continues within the run limits. The human reviewer must check every destination, privilege, side effect, and credential exposure; scope validation of the selected host does not prove that an arbitrary program cannot reach other destinations. The server rechecks scope, host approval, and the generated command immediately before every automatic catalog execution. The tool catalog contains names and purposes, not command templates. Catalog registration alone does not authorize an arbitrary command. If a generated catalog command fails validation, Yagura reads the local man page when available and asks the model to rebuild it once; a second failure stops safely. AI investigation has no check-count limit. A one-host run has a 1,200-second active-execution limit per segment; time waiting for human review is excluded. Scope checks, the stop action, and separate approval for unlisted tools remain. A run also stops on failure, no response, import warning, changed scope, or invalid model selection. The chronological decisions, results, evidence links, and stop reason are saved in `data/autonomy.json` (last 20 runs). The technical AI investigation log also shows recent model-call measurements from `data/llm-metrics.json`: model, duration, input/output character counts, requested output cap, finish reason, and token counts when the gateway reports them. This bounded log stores no prompt or response text. Server restart marks an in-progress run interrupted; it does not resume automatically. The AI model endpoint must be configured separately. This is a bounded investigation assistant, not autonomous credential acquisition.

**Multi-host AI survey** selects recorded and approved hosts under the saved scope without a host-count cap. It proposes one tool check for each host. Validated catalog commands run automatically; unlisted tools pause for human approval. Hosts without a justified tool check are skipped. After every imported result, the model sees only that check's redacted evidence and linked findings for the same host. It may add one evidence-linked review flag for that result or no flag. The server rejects unknown IDs, another host's evidence, and unlinked citations; a flag-review failure is logged without discarding the command result. After the survey, Yagura chooses an evidence-backed host for a deep dive. Recently recorded identical commands are skipped for 24 hours. The run has no check-count limit and a 1,800-second active-execution limit per segment. Scope and host identity are checked before each check. Historical comparison events remain readable, but new runs record check-level flag reviews in `data/autonomy.json`.

**Evidence-linked review flags** appear in Findings after each result is imported. Yagura derives them from the current saved inventory and approved scope, including OS fingerprints, identified software and versions, selected web exposure responses, login forms, and anonymous SMB share listings. Each flag links to the exact finding and source evidence. Corrections, deletion, new results, and scope changes update the list on refresh. These are review leads rather than confirmed vulnerabilities; no priority score is assigned yet. The flags do not authorize or execute follow-up commands. `GET /api/attention` returns the current scoped list.

**Version-matched vulnerability candidates** use the bundled, offline [`backend/vulnerability_catalog.json`](backend/vulnerability_catalog.json) snapshot (dated 2026-10-21). It contains selected upstream advisories from the [NGINX security list](https://nginx.org/en/security_advisories.html) and [Apache HTTP Server 2.4 list](https://httpd.apache.org/security/vulnerabilities_24.html). Yagura compares explicit three-part versions from approved, open services and their linked Nmap/HTTP evidence against the catalog's branch-aware affected intervals. Findings displays the possible CVE, exact observed version, advisory link, evidence, and configuration condition. New or corrected evidence is compared on refresh; this makes no target request and sends no evidence to a vulnerability service. The bundled list is intentionally incomplete and changes only when its JSON is reviewed and updated in the XS repository, tested, and redeployed. A missing match is not a safety verdict. Distribution packages may backport fixes without changing the upstream version banner; verify package release, enabled modules, configuration, and vendor advisory before confirming any finding. `GET /api/vulnerabilities` returns the current scoped comparison and catalog date.

**Investigation chat** fills the available page height with a scrollable conversation and visible composer. The saved cross-host picture, next checks, and latest run are compact disclosure sections above the operator's questions. A Latest messages button appears when reading older turns. Settings holds the model and refresh controls. Source buttons open the stored finding or original evidence. Follow-up questions first read a sanitized overview of approved hosts, then the model selects up to eight relevant hosts whose saved evidence is read in detail; the answer displays both coverage counts. If model discovery is temporarily unavailable, the selector also shows model IDs recorded in prior runs; the server verifies any selected ID against the gateway before use. `POST /api/briefing/ask` validates that every cited finding has linked evidence supplied to the model. An ungrounded reply is retried once, then rejected if still ungrounded. Briefing requests allow up to 32,768 output tokens so reasoning-capable models can finish; the returned answer and citation counts remain bounded by response validation, and the gateway may impose a lower limit. Asking a question reads saved data and never runs a target check. The separate **Investigate** action accepts a natural-language goal. An exact saved hostname or IP resolves directly. If the instruction names multiple hosts or no exact host, a dialog offers eligible saved targets as buttons and an Other field to correct the instruction; no check begins until one target is chosen. Yagura then shows the DNS status and pinned IP for confirmation, asks for explicit approval when the inventory pair was not yet approved, and starts a goal-directed run. Each step selects a tool, proposes a bounded check, observes saved evidence, and replans from the result until no justified check remains or the run stops. The run history records the goal, plan, observations, and stop reason; the chat displays them as the investigation progresses and after a reload. Catalogued commands follow the existing target and option validator; unlisted tools still pause for exact human review. A broad request such as “演習対象の全ホストに対してポートスキャンして” is recognized as an all-host port scan. The chat previews every distinct approved IP/name target in the saved scope, the TCP top-100 profile, and the number of unapproved hosts excluded. After confirmation, the server checks that the approved target set is unchanged and runs one validated Nmap TCP connection scan per host, saving each result in the conversation and findings. Individual host failures are recorded and do not skip the remaining hosts; a 30-minute segment can be continued from the chat. This path does not scan unapproved hosts or every address in a CIDR, and it does not depend on the model selecting Nmap. A candidate selected from the bounded catalog can be reviewed and approved within Briefing: the UI fetches the current command and target, and the server checks the approved scope and exact displayed command again before execution. Model answers are hypotheses, and conversation turns stay in the current browser session; refresh clears them. A model outage does not prevent the saved briefing from loading.

**Authorized inventory** in Scope accepts a local Providentia HTML export, a two-digit team number, a hostname suffix, and optional internal resolver IPs. It expands team placeholders, keeps concrete IP/name pairs inside the saved scope, and lists unresolved templates separately. With resolvers, exact A plus PTR confirmation is labeled DNS verified; an empty A answer is labeled inventory-only. Without resolvers, pairs are labeled inventory-only without a DNS check. DNS mismatches, resolver failures, PTR review needs, and IP conflicts remain ineligible. The HTML file is parsed without being saved; scoped pairs and DNS evidence are persisted in `data/discovery.json`. The operator explicitly approves exact eligible pairs in a confirmation that identifies DNS status. Inventory-only approval records its provenance and pins subsequent checks to the listed IP; it does not claim DNS identity verification.

**Investigate hosts** accepts one or more approved hosts from the saved scope. One selected host starts the existing AI deep-dive loop immediately. Multiple selected hosts receive one baseline result and review decision per host, then Yagura chooses a deep-dive host. A multi-host survey pauses after a 1,800-second segment with completed hosts saved; Continue resumes the remainder. **Survey inventory** visits every approved inventory host in batches of four and has the same resumable survey behavior. Once all hosts are surveyed, Yagura selects an evidence-backed host for the existing deep-dive loop. Validated catalog commands run automatically; unlisted tools still require separate human approval. **Discover scope** remains available for CIDR-based discovery: it scans each saved CIDR in at-most-16-address Nmap segments, persists progress, and pauses for DNS/name approval when needed. After continuation it surveys all approved scoped hosts, with a host from each CIDR first. A changed scope or host identity stops execution. Neither mode approves a DNS identity automatically or scans outside its authorized targets.

A ping with complete statistics but zero replies is shown as **No response**, not **Failed**. Its observation is still saved, and an automatic run stops before the next check; no ICMP reply does not prove the host is down. Tool errors and results that cannot be imported remain **Failed**.

The reference catalog still describes ffuf and Nuclei, but neither is offered as an executable check. The four bounded Kali adapters below are manual checks with fixed targets and parameters. Their application-level pinning is not a substitute for a host firewall or isolated network namespace; do not enable broader third-party scanners, a browser crawler, or automatic execution of these adapters before an independently tested egress boundary is installed.

Optional local LLM configuration uses an OpenAI-compatible endpoint:

```env
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_MODEL=
LLM_API_KEY=
```

Copy `.env.example` to `.env` and set the endpoint. The Analysis view lists models advertised by that endpoint; the selected model is used for analysis and suggestions. `LLM_MODEL` remains an optional server default. By default, only localhost or literal private/local IP endpoints are accepted; redirects are refused. Command ranking receives stored finding summaries and eligible fixed checks. AI investigation uses installed tool names, reads the selected catalogued tool’s local help, and can consult its man page to rebuild a rejected command. Unlisted tools require human review without automatic help execution. Findings analysis also receives bounded excerpts from linked raw evidence. It selects candidate IDs, while the server supplies verified commands, reasons, and evidence links. If `LLM_MODEL` is empty and `/models` advertises exactly one model, the service selects it automatically; with multiple models, choose one in the UI. Invented commands or unsupported targets cannot pass through. Built-in checks remain available if the model is missing, unreachable, or returns invalid results.

For an explicitly trusted gateway DNS name, set `LLM_BASE_URL` to its HTTPS `/v1` URL and `LLM_TRUSTED_HTTPS_HOST` to that exact hostname. HTTP, other DNS names, credentials in the URL, query strings, fragments, and redirects remain blocked; HTTPS certificate verification remains enabled. Only sanitized, bounded evidence excerpts are sent to the configured gateway during analysis; explicitly marked sensitive evidence bodies are excluded. Keep `LLM_API_KEY` in the untracked `.env` file with owner-only permissions.

## Published website contacts

For a recorded open TLS service, **Inspect TLS certificate** runs the fixed Nmap `ssl-cert` script on the recorded TCP port, imports its XML output as linked evidence, and is no longer suggested after a certificate result is saved. Certificate names are observations, not newly approved targets.

For a recorded open HTTP(S) service inside the authorized check range, **Next checks** can suggest **Inspect published website contacts**. Set the host record's **Hostname** to the exercise site's actual name (for example `www.exercise.test`) when it uses virtual hosting. The command keeps that name for HTTP Host and TLS SNI but pins the connection to the recorded, scoped IP. HTTPS certificate verification remains enabled.

The executable command is `python3 -m backend.web_contacts --url <website-url> --ip <recorded-ip>`. The app constructs its arguments from the stored host and service; it does not accept arbitrary URLs or commands in the execution request. The standalone command accepts only private, shared, or local IPv4 addresses. The app additionally enforces the saved CIDRs and domains before invoking it.

The check reads page text and `mailto:` recipients, deduplicates addresses, and follows up to five same-origin pages (contact/about links first). Other origins, ports, URL credentials, and external redirects are rejected; no JavaScript or forms are executed. Limits are 256 KB per page, 25 distinct addresses, and a bounded request duration. The report and source URLs are saved as linked findings/evidence. Zero, one, or multiple addresses refer only to inspected pages; this does not prove whole-site uniqueness. Fetch errors and incomplete coverage remain visible in the evidence.

## Email drafts

Open **Email drafts** to select a discovered contact or enter a recipient manually. The sender address and name are optional so you can prepare messages before exercise infrastructure is confirmed. Edit the subject and plain-text body, save and reopen drafts, preview them, or copy their text. **Export .eml** saves the current draft and downloads a MIME message with `X-Unsent: 1`; unknown sender details are omitted. Internal notes and source evidence are excluded from exported messages.

**Suggest wording** uses the drafting brief and optional existing subject/body with your configured local model. It previews the suggestion and applies it only after **Use this wording**. Generation does not save the draft, send email, or configure sender infrastructure. Manual editing works without a model. This release has no SMTP transport or email delivery endpoint.

Drafts are stored separately in `data/email-drafts.json` with recipient source references derived from saved contact findings. Conflicting edits from another browser tab are rejected rather than overwriting newer content. Drafts are not part of the findings JSON/CSV export; use `.eml` export for messages. The API provides `GET/POST /api/email-drafts`, `PATCH/DELETE /api/email-drafts/{id}`, `GET /api/email-drafts/{id}/export`, `GET /api/email-contacts`, and `POST /api/email-drafts/generate`.

## Target scope and server diagnostics

The check catalog also offers **WhatWeb**, **Gobuster**, **sslscan**, and **dnsrecon** when their binaries are installed. Each check requires a saved scope, an approved host, and a recorded open service. WhatWeb and Gobuster use a loopback proxy pinned to that service IP and port; redirects are not followed, and request counts and runtimes are bounded. Gobuster is offered only after saved web routes, form metadata, or discovery hints identify a reason to inspect more paths; its bundled list has 19 paths. The installed WhatWeb disables TLS certificate verification, so its check is offered only for HTTP. Gobuster retains TLS verification for HTTPS. sslscan connects to the selected literal IP, uses the approved name for SNI, and records enabled protocols and accepted cipher suites. dnsrecon offers distinct zone choices from the approved resolver name and saved domain scope; it queries the selected resolver over TCP without zone transfers, brute force, or external OSINT. Returned names are observations, not approved targets. These four catalog checks require a human click to run and are not part of the automatic loop.

The catalog also offers fixed Nmap `ssh2-enum-algos` and `rdp-enum-encryption` checks for recorded open SSH and 3389/tcp services. They save script output as linked evidence. A script result is a configuration observation, not proof of a vulnerability.

- Optional **Yagura server network** diagnostics run `ip -j -4 addr` and `ip -j -4 neigh` and save results as linked findings/evidence for server context without changing the target scope.
- Nmap discovery runs with `-n -sn --max-rate 5 --max-retries 1` after authorization is checked. The target must be contained in a saved CIDR. Results stay quarantined until DNS review and approval; discovery never changes the saved scope.
- Passive imports may contain other addresses. Scope matching defaults to **AND**: a host must match a saved CIDR and, when configured, a domain suffix. **OR** permits a private/shared IPv4 host matching either one; public IPv4 is never executable. With domains configured, DNS review and explicit IP/name approval are still required in either mode. A private address or neighbor entry alone does not establish authorization.
- In OR mode, `POST /api/discovery/name` looks up one authorized hostname using only resolver IPs inside saved CIDRs. It quarantines private/shared A results without connecting to them. Review PTR and A records via `POST /api/discovery/dns`, then approve the host before running checks. Raw range discovery remains CIDR-contained.
- Keep the app bound to localhost unless you add access controls. Public asset serving excludes configuration, source modules, and the data directory.

## Validate

```sh
python3 -m unittest discover -s test -p 'test_*.py'
```

Python tests cover the parser, record merging, API persistence, scope limits, and analysis fallback. No real scans or model are required. The Python backend is the only server implementation. `npm start` and `npm test` are optional shortcuts for the Python commands above; Node.js is not required when running Python directly.

## Findings analysis backend

Context selection reserves linked host and service evidence before higher-priority observations, so a dense web survey cannot crowd out every host from a group analysis. DNS approval records are shortened to the approved IP/name pair in the model input; the full resolver review remains in stored evidence. If no linked evidence fits, analysis reports `no-context` instead of a successful empty model result. The bounded context can still omit findings; check its truncation warning before relying on a cross-host hypothesis.

Use **Findings analysis** in the UI to analyze all recorded findings or one host. **Test model connection** checks the endpoint and model list. Each interpretation links to the supplied findings and evidence and is labeled as a model hypothesis requiring review. Missing services, authentication evidence, and other uncertainties are returned separately. The latest analysis is saved locally in `data/analysis.json`; edits/imports mark it stale. The analysis service never runs target commands. The model's JSON-object mode does not enforce the analysis field schema: Yagura validates fields and evidence links itself, retries a malformed or ungrounded reply once with a stricter format request, then falls back to recorded facts if validation still fails. Error details name only invalid fields and types, not model-generated values.

Responses contain `status`, `source`, `model`, `scope`, `counts`, `summary`, `assessments`, `suggestions`, `snapshotId`, `generatedAt`, `stale`, and `warnings`. Assessments have `findingIds`, `evidenceIds`, `interpretation`, and `uncertainties`. References must point to evidence supplied to the model and linked to each cited finding. Suggestions resolve only to server-generated eligible commands. Citation validation checks references, not the factual correctness of model prose.

Analysis uses a bounded context (up to 60 findings, 12 deduplicated evidence excerpts, and 10,000 characters). Select one host, all approved hosts, or a related group of up to eight approved hosts; evidence selection reserves a first pass across hosts before filling remaining slots. Evidence is sanitized before model submission. Unsupported model items are rejected individually when other grounded items remain. Output errors, connection failures, timeout, and authentication errors return `status: "fallback"`, `source: "built-in"`, and an explicit error code. Concurrent requests for the same snapshot share the in-flight model request. `LLM_TIMEOUT_MS` defaults to 30,000 and is capped at 600,000 per model request.

For a live local model check, use **Test model connection** in the Analysis view.

## Evidence-driven path hypotheses

Findings analysis now asks the local model to infer possible paths from collected evidence,
including relationships across hosts when **All stored findings** is selected. No exercise-specific
paths are embedded in the analysis rules. Each hypothesis contains ordered, cited steps,
prerequisites, missing evidence, counterevidence, and proposed investigations with expected
results and their impact on the hypothesis. Step status is the model's assessment, not a
server-verified exploitation result. The server validates the shape and supplied references.
Hypotheses are saved with the existing analysis snapshot and become stale when findings change.
Reanalyze after importing new evidence; this version recomputes hypotheses rather than maintaining
a longitudinal hypothesis history. A model outage shows recorded facts and existing checks,
without synthesizing attack paths.

Use **General investigation evidence** in Import command output for transcripts, configuration
excerpts, authentication results, or other text without a dedicated parser. Supply an evidence
title, optional numeric host IP, source command and observation time. No source command is executed.
Mark an item sensitive to replace its body and linked detail with a redacted marker at save time.
Known key/value credentials, authorization headers, and private keys are also redacted on save,
API responses, AI context, and JSON/CSV export. Pattern matching cannot identify every secret;
review existing raw files and mark sensitive imports explicitly. Existing files are sanitized
when subsequently saved, not silently rewritten on startup.

Proposed investigations can describe checks beyond the executable catalog. They are displayed
for manual review and have no Run button. Executable suggestions still resolve to server-generated
candidates and use the existing scope and execution checks. Analysis context remains bounded;
truncation is reported, and long evidence excerpts include the beginning and end. Detailed evidence
selection, automatic collection for new investigation types, and hypothesis history remain future work.

## Investigation catalog additions

The reference catalog now includes bounded route discovery, exposed configuration and Git-source
review, backup comparison, single known-credential SSH verification, process and KeePass inspection,
Windows identity, JEA connection and command discovery, routine metadata and existing output,
PFX metadata, signature status, MySQL grants/file policy, web process ownership, document response
comparison, and read-only SQLite inspection. These are reference templates requiring manual
execution and General investigation evidence import. They do not encode an expected attack path.

A new executable **Inspect web metadata exposure** check uses the existing IP-pinned transport and
verified TLS to issue six fixed GET requests (Git HEAD, WEB-INF configuration, library listing,
docs, and a missing-page baseline). Responses and errors become evidence, without an automatic
vulnerability verdict. Web inventory also records form actions, methods, encoding and field names,
and query parameter names without submitting forms or retaining field values. Existing scope and
per-check authorization apply. No new third-party dependencies are installed by the application.
Credential guessing, memory dumping/recovery, password cracking, payload execution and signed-job
submission have not been added as executable checks in this increment.

### Natural-language host groups

Investigation chat can select several hosts from saved evidence when the instruction names a
service category (Web, SSH, SMB, RDP, DNS, mail, or database) and asks about hosts or targets.
For example, “Webサービスがあるホストに対して調査して” selects only approved hosts with a
recorded open Web service. The confirmation dialog lists every selected hostname, IP, and
matching service before execution. “全ホスト” without a service condition selects all approved
saved hosts. A matching port-scan request uses the bounded TCP top-100 profile for the selected
set; other requests start an AI survey and carry the original goal into tool selection.
The server recalculates the selected set at start and rejects stale previews. Missing open-service
evidence yields no automatic selection; survey or import results first, then retry.
